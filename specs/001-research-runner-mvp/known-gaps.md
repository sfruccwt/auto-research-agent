# Known Gaps — Research Runner MVP

首次测试 run（ai-trust-layer, 2026-04-29 ~ 2026-05-06）中暴露的设计缺口与待收尾事项。

---

## 一、Idea 生命周期管理

当前设计假设 idea 与 run 是 1:1 的关系：一个 idea 进来，跑一个 run，投递一个 output。实际测试中出现了三种 1:1 之外的情况：

### 1.1 Idea 合并

研究过程中发现两个 idea 实质上是同一个问题的不同面。例如本次 "ai-trust-layer"（人类审查锚定在哪一层）与 "spec 文档怎么写" 高度关联——前者的结论是"锚定在 spec 层"，后者是它的自然延伸。

待决：
- 合并后的 run 引用哪个 idea？两个都引用？
- 合并后投递的 output 的 `source_idea` 字段怎么写？
- wiki 侧两个 idea 的 status 怎么处理？

### 1.2 Idea 派生

一个 run 过程中会联想出新的研究点。本次测试派生了至少三个：
- "spec 文档体系具体怎么写"（从结论直接引出的下一步）
- "事前约束 vs 事后测试的关系"（memo 中的一个偏向引出的独立课题）
- "motivation 该细化到什么颗粒度"（SOP 层面的方法论问题）

待决：
- runner 是否应该有"回写新 idea 到 wiki"的通道？当前设计 wiki 是只读的（除 inbox）
- 如果开通道，写到 `research/ideas/` 还是 inbox 里附带？
- 派生 idea 与母 idea 之间需不需要显式关联？

### 1.3 课题纵深 / 多级课题

一个粗粒度的 idea 被快速解决后，结论指向一个更细的子问题。这不同于"合并"（横向），而是"往下钻"（纵向）。

待决：
- 是把子课题当新 idea 重新走流程？
- 还是在同一个 run 里继续深入，最终产出一个多层的 output？
- 或者保留一种"结项 + 派生"机制：母课题一句话结项，子课题自动作为新 idea 进 queue？

### 1.4 Idea 直接在 runner 侧产生

当前设计假设 idea 只从 wiki `research/ideas/` 单向流入 runner。但实际使用中用户可能直接在 runner 工作区说"我想查个东西"就要启动研究，不想先去 wiki 写 idea 文件再拉过来——流程太重。

待决：
- runner 是否应支持"就地创建 idea"——用户口述一句话，runner 直接建 run 目录开跑？
- 如果支持，这个 idea 需不需要同步回写到 wiki `research/ideas/`？还是只存在于 runner 本地？
- `source_idea` 字段（FR-016）在没有 wiki 侧 idea 文件时怎么处理？
- 与 1.2（派生）的关系：派生 idea 也可能直接在 runner 侧产生并立即开跑，而不是先回写 wiki 再拉回来

## 二、结题 / 结项机制

当前 spec 假设 run 只有两种终态：delivered 或 abandoned。实际测试中出现了第三种：

**课题已有结论但不适合直接投递。** 本次 run 的结论（"审查锚定在 spec 文档层"）是明确的，但：
- 后续发现这个结论需要一个更大的课题来展开（怎么写 spec）
- memo 的质量不足以直接投递（太泛、有立场偏差）
- 课题方向发生了根本转向，原始 memo 的框架不再适用

待决：
- 是否需要一种"轻量结项"状态——记录结论，但不产出正式 output？
- 轻量结项的产物是什么？一段话写在 log.md 里？还是一个精简版 output？
- 轻量结项后，run 目录里的中间产物（task-card、judgment、memo）怎么处置？保留作参考？

## 三、SOP 改进的收集位置

测试中发现的 SOP 问题已记录在 `sop/backlog.md`（共 8 条待改进）。但 backlog 与 spec 之间的关系不明确：

- backlog 条目中有些是 SOP 模板层面的改动（如去掉"不可信信息跳点"字段）
- 有些是流程层面的改动（如 motivation 持续捕获机制）
- 有些是工具层面的（如搜索路径默认开 agent-reach）

待决：
- 这些改动是在现有 spec 下直接修 SOP 文件？还是需要一个新 spec（如 `002-sop-refinement`）来规范？
- MVP 阶段怎么判断 backlog 条目的优先级？
