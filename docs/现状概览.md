# Auto Research Agent — 现状概览

> 写给使用者的快速上手指南。帮你在 5 分钟内理解"这个工作区是干什么的、怎么运转的、关键节点有哪些"。

---

## 一句话定位

一个**结构化研究执行工作区**：把模糊的研究想法，经过开题→搜索→判断→收题的流水线，产出可以直接行动的研究结论，最终投递到 Wiki 知识库。

核心信念：**研究是为了做决策，不是为了囤信息。**

## 三道门：研究过程的关键节点

整个研究过程被三道"门"（Gate）切分。每道门都有明确的准入条件和产出物，**过不了门就不能往下走**。

### Gate 1：开题门 — "你到底要研究什么？"

**核心问题**：这次研究支持什么决策？比较哪些路径？不回答什么？

**做的事**：
1. **关键词压力测试**：对研究主题中的每个关键词，从三个维度确认范围——
   - 主语（谁？）
   - 领域（在哪个场景下？）
   - 动作（具体做什么？）
   
   目的是把模糊的大词拆成有边界的小词。比如"本地部署 embedding 模型"——谁部署？个人开发者还是企业？部署到哪？笔记本还是服务器？部署来做什么？语义搜索还是 RAG？

2. **列出要比较的路径**：至少 2-3 条可选方案，这些路径就是后续搜索的骨架。

3. **填写任务卡**（task-card）：记录以上所有确认结果。任务卡的"真正要回答的问题"栏允许先粗后细——开题时写个大致版本，第一轮搜索后再回来修。

**产出物**：`notes/task-card.md`

**关键逻辑**：如果你对研究领域不熟，runner 会先做一轮快速搜索来帮你理解领域，然后再反过来问你问题，而不是让你凭空回答。这是"迭代式开题"。

---

### Gate 2：中途门 — "看了一圈之后，你怎么想？"

在第一轮广域搜索完成后、第二轮深入搜索开始前触发。

**做的事**：

1. **立刻写判断**（judgment）：不等搜完才写，而是在第一轮结束时就要求形成初步判断——
   - 我目前认为什么？
   - 哪条路径最优？
   - 最短证据链是什么？（从结论到源头，能用几步说清楚）
   - 什么信息能推翻这个判断？

2. **动机校准**：把搜到的东西反馈给你，问——
   - "这些发现跟你的实际情况有什么关系？"
   - "有没有你之前没提到的约束条件？"
   
   为什么要这一步？因为人在看到实际信息之前，对自己的需求往往是不完整的。看到了之后，问题会自然演化。

3. **子课题分拆检查**：如果某个概念需要单独深入研究才能支撑主课题的结论，runner 会标记出来，由你决定是否拆成子 run。

**产出物**：`notes/judgment.md`

**关键逻辑**：判断先行。不是"搜完再想"，而是"搜一轮就必须表态"，然后用第二轮来验证和修正这个表态。

---

### Gate 3：收题门 — "能行动了吗？"

第二轮搜索完成后，进入收题。

**做的事**：

1. **确定行动上限**：当前证据到底支持做到什么程度？
   - 能直接选一条路走了？
   - 还是只够比较、不够选？
   - 还是连比较都不够、需要继续观察？

2. **给出推荐**：推哪条路？为什么？

3. **定义最小下一步**：不管结论如何，下一步最该做的一件事是什么。

4. **写翻转条件**：什么证据出现了，当前结论就该推翻。

**产出物**：`notes/memo.md`（内部工作文档）→ 然后决定走哪条路——

| 走向 | 条件 | 产出 |
|------|------|------|
| **投递** | 结论足够支撑行动 | `output.md` → Wiki 收件箱 |
| **轻量结项** | 有结论但不值得投递（比如是子课题、或方向发生了转变） | `notes/closing-summary.md` |
| **放弃** | 研究方向被证伪或不再有意义 | 记录原因，归档 |

**关键逻辑**：memo 和 output 是两个东西。memo 是给你自己看的工作底稿（记录思考过程），output 是给 Wiki 读者看的成品（结论先行、展开关键概念、去掉过程性语言）。从 memo 到 output 需要一次"变换"，不能直接复制。**memo 写完后必须交用户审阅确认，然后才能写 output。**

## 研究过程中的核心思维动作

### 观点拆解（第一轮搜索后）

对每个值得深入的观点，拆成四层：
1. **结论**：它在说什么？
2. **逻辑链**：它怎么得出这个结论的？
3. **支撑证据**：靠什么事实/数据/案例？
4. **前提条件**：哪些假设必须成立？

### 主动找反面（第二轮搜索，强制要求）

对每个观点 A，必须去看：
- 谁支持 A？
- 谁反对 A？反对的是 A 的逻辑还是事实？
- 反对者的攻击打在中心论点上还是边缘情况上？

这不是可选步骤，是强制的。反面观点往往暴露出正面观点没说清的前提。

### 证据分级

| 层级 | 含义 | 可信度 |
|------|------|--------|
| 一手/官方 | 官方文档、原始数据 | 最高 |
| 市场/新闻 | 行业报告、新闻报道 | 中高 |
| 学术 | 论文、综述 | 中高 |
| 社区 | 论坛、博客、经验帖 | 参考 |

每条引用的证据都要标注层级，不能混着用。

## 树状研究：详细机制

这是整个系统最有设计感的部分。传统研究工具要么是线性的（一个问题研究到底），要么是发散的（想到哪搜到哪）。这个系统的做法是：**允许研究在中途分叉，但每个分叉都是独立的、有结构的 run，最终结论汇聚回母课题。**

### 什么时候会触发分叉？

在中途门（Gate 2）有一个专门的检查步骤叫**子课题分拆检查**。它的判断标准是：

> 如果某个子概念需要独立深入研究，才能支撑母课题的结论——那它就该拆出去。

举例：你在研究"本地部署 LLM 的最优方案"，搜索过程中发现"量化精度对实际使用的影响"这个点很关键，但现有资料说法不一，需要专门研究。这时 runner 会标记它，问你：要不要为这个点单独开一个 run？

**决策权在你和母 agent**。runner 标记和提议，你决定是否拆分。母 agent 在判断子任务需要独立研究流程时，也可以自主决定开子 run。

### 检索任务 vs 独立子课题

不是所有子 agent 执行的任务都需要开 run：

| 类型 | 特征 | 是否开 run |
|------|------|-----------|
| **检索任务** | "帮我搜一下 X 的文档""查社区有没有人讨论过 Y" | 不开。结果直接返回母 agent，整合到母 run 的 notes/ 或 sources/ |
| **独立子课题** | 有独立研究问题，需要完整的开题→搜索→判断→收题流程 | 开。用 `new-run.ps1 -ParentRunId` 建在母 run 的 `sub/` 目录下 |

### 分叉后发生什么？

1. **记录**：子课题被写入母 run 的 `notes/derived-ideas.md`，格式包含标题、一句话描述、与母课题的关系。

2. **开子 run**：用 `new-run.ps1 -ParentRunId <母run-id>` 为子课题建一个独立 run。子 run 目录位于母 run 的 `sub/` 下，不带日期前缀。它拥有自己完整的开题→搜索→收题流程，跟母 run 结构完全一样。

3. **母 run 的状态**：母 run 不需要"暂停"——它可以继续做其他方向的搜索。但在写收题判断时，如果子课题的结论是关键依据，就需要等子 run 完成。

### 结论怎么回流？

子 run 完成后（无论是投递还是轻量结项），runner 会提示你三个选项：

| 选项 | 说明 |
|------|------|
| **回填结论** | 把子 run 的关键结论（1-3 句话）追加到母 run 的 `notes/child-results.md` |
| **更新派生记录** | 在母 run 的 `derived-ideas.md` 中回填子 run 的 ID，建立关联 |
| **不回填** | 你判断子课题的结论对母课题不重要，跳过 |

回填后，母 run 在做第二轮搜索和收题判断时，可以直接引用子 run 的结论作为已验证的输入，不需要重新研究那个点。

### 为什么子 run 通常走"轻量结项"而不是"投递"？

子课题的研究结论往往：
- 太窄，单独发到 Wiki 没有独立阅读价值
- 本身就是母课题的一个组成部分，最终会融入母课题的 output

所以子 run 更常见的归宿是**轻量结项**（close）——有结论、有记录，但不单独投递。结论通过回填机制汇入母课题，随母课题一起投递。

### 可以嵌套多深？

理论上没有限制。子课题 A 在研究过程中也可能发现需要拆分的子子课题 C，形成多层树。但实际使用中，两层（母→子）已经能覆盖绝大多数场景。如果嵌套超过两层，可能意味着母课题的范围定义需要收窄。

### 树状研究的本质

把它想成一种**深度优先的研究策略**：遇到关键但不确定的子问题时，先深入解决它，拿到确定性结论，再回到上层继续。每个节点都是一个完整的、有门控的研究过程，不是随意的发散搜索。这保证了：

- **每个分叉都有结构**：不会出现"搜着搜着就跑偏了"的情况
- **结论有明确的汇聚点**：子课题结论回填到母课题，不会散落在各处
- **进度可追溯**：每个 run 有自己的 log，中断后可以恢复

## Run 的生命周期状态

```
created → researching → drafting → revising → delivered
                                            → closed（有结论，不投递）
                                            → abandoned（中止）
```

每个状态变更都记在 `log.md` 里，所以中断后可以恢复——读 log 就知道上次走到哪一步了。

## Idea 的两个池子

| 池子 | 位置 | 特点 |
|------|------|------|
| Wiki 池 | `D:/Personal LLM Wiki/research/ideas/` | 长期孵化、跨项目 |
| 本地池 | `ideas/` | 临时的、跟当前工作直接相关 |

两种启动方式：
- 指定已有 idea 文件 → 从 Wiki 池或本地池拿
- 口头说"我想研究 X" → 自动在本地池建 idea 文件并开 run

## 工具层（不展开细节，只说职责）

| 脚本 | 干什么 |
|------|--------|
| `new-run.ps1` | 建 run 目录、冻结 idea 快照、初始化 log、加入队列。支持 `-ParentRunId` 参数创建子 run |
| `deliver.ps1` | 校验 output → 复制到 Wiki 收件箱 → 更新队列状态 |
| `close-run.ps1` | 写结项摘要 → 更新队列状态（不投递） |
| `scan-and-align.ps1` | 扫描两个 idea 池 + 所有 run，分类汇报当前全局状态 |
| `queue.ps1` | 底层队列读写，被其他脚本调用 |

## 每个 Run 目录里有什么

```
runs/<run-id>/
├── idea.md                  ← 冻结的研究主题快照
├── log.md                   ← 事件日志（状态变更记录）
├── notes/
│   ├── task-card.md         ← 开题门产出：任务卡
│   ├── judgment.md          ← 中途门产出：判断声明
│   ├── memo.md              ← 收题门产出：决策备忘录
│   ├── closing-summary.md   ← 轻量结项时的总结
│   ├── derived-ideas.md     ← 研究中发现的子课题
│   └── child-results.md     ← 子 run 结论回填
├── sub/                     ← 子 run 目录（按需创建）
│   ├── <child-slug>/        ← 子 run（不带日期前缀）
│   │   ├── idea.md          ← 含 parent_run 字段
│   │   ├── log.md
│   │   └── notes/
│   └── ...
└── output.md                ← 最终产出（投递到 Wiki 的成品）
```

## 快速参考：七问审计清单

在任何阶段都可以用这七个问题检查研究质量：

1. 这次研究支持什么决策？
2. 在比较哪些路径？
3. 我目前的判断是什么？（第一轮后）
4. 最优路径是哪条？（第一轮后）
5. 证据链站得住吗？（第一轮后）
6. 当前证据支持做到什么程度？（收题前）
7. 推哪条路？为什么？（收题前）
