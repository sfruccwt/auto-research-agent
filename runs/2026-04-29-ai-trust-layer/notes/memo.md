# 决策导向研究备忘录：Vibe Coding 中人类应把控到哪一层

## 这次要支持的决定
在 AI 辅助开发个人工具/自用 demo 时，确定一个可操作的"人类把控层级"原则：哪些层必须审、哪些层可以放手。

## 当前判断

**你现在的做法（路径 A：让 AI 总结实现逻辑，自己不读代码）对个人工具场景基本合适，但需要在一个方向上补强：在让 AI 生成代码之前，先告诉它项目的结构规则——哪些功能放哪个文件、模块之间怎么调用、命名用什么约定。这比事后去审查代码有效得多。**

### 为什么是"生成前约束"而不是"生成后审查"

个人工具场景下，最大的风险不是安全漏洞，而是**三个月后回来改不动**。这是因为 AI 生成代码时，文件之间的关系、组件之间的依赖、为什么这样设计而不那样设计——这些信息只存在于当时的 AI 上下文窗口里。代码本身不记录这些关系。人回来后看到一个 600 行的文件混合了渲染、数据处理和 API 调用，不知道能不能安全地拆开或修改其中一部分。

事后审查解决不了这个问题，因为审查的前提是代码已经写成了某种结构。如果 AI 一开始就把不相关的功能塞进同一个文件、创建了循环依赖、或者重复造了轮子，事后发现了也只能重写。

而如果在生成前就告诉 AI "认证逻辑放 auth/ 目录、数据处理放 data/、不要在 UI 组件里直接调 API"，AI 大概率会遵守这些约束，生成出的代码天然就是可维护的结构。

### "生成前约束"具体是什么、写到什么程度

就是在项目的 `CLAUDE.md`（Claude Code）或 `.cursor/rules/`（Cursor）中写明项目的结构规则。

#### 写多少：收益递减的实证数据

社区实践和多个来源一致指向一个收益递减曲线：

| 规则数量 | 效果 | 来源 |
|---------|------|------|
| **0-4 条** | 覆盖 80% 的常见问题 | Karpathy 的 CLAUDE.md（GitHub 6 万+ 星标）只写 4 条行为准则 |
| **5-15 条** | 每条仍有明显增量价值 | Cursor 官方建议 1000-2500 词为甜区 |
| **15-30 条** | 开始出现规则间冲突和遗忘 | HumanLayer 分析：LLM 在总指令 150-200 条时开始衰减 |
| **30+ 条** | 收益显著递减，重要规则被淹没 | Cursor 论坛反馈：10 行核心规则比 2000 行巨型文件效果好 |

**对个人工具项目：20-40 行足够。** 超过 80 行后 Claude 会开始忽略部分内容（HumanLayer 数据）。

#### 什么必须写、什么不用写

**必须写（AI 不写就会犯的错）：**
1. **项目做什么**：一句话描述，让 AI 理解上下文
2. **技术栈**：语言、框架、包管理器——防止 AI 猜错
3. **常用命令**：dev / test / build 的具体命令
4. **文件/模块边界**：哪类功能放哪个目录。这是防止"600 行单体文件"的核心规则
5. **项目特有的坑**：只有你踩过才知道的陷阱

**按需写（踩过坑再加）：**
- 依赖方向（防循环依赖）
- 命名约定（防换模型后风格漂移）
- 复用规则（防 AI 重复造轮子）

**不用写（交给工具或 AI 自己就会）：**
- 代码风格细节（交给 linter/formatter）
- "写干净的代码"之类的泛泛要求（没有约束力）
- AI 能从代码中自己读出来的信息
- 完整的 API 文档（改为链接引用）

关键原则来自 HumanLayer："**只有在聊天中重复了同一个指令两次以上，才应该把它提升到 CLAUDE.md 中。**"

#### 个人工具项目的最小模板

```markdown
# 项目名称
一句话：这个工具做什么。

## 技术栈
- 语言：Python 3.12
- 框架：FastAPI
- 包管理：uv

## 常用命令
- `uv run dev`：启动开发服务器
- `uv run test`：跑测试

## 项目结构规则
- 数据获取逻辑放 `services/`，不要在路由处理函数里直接写
- 配置和常量放 `config/`
- 工具函数放 `utils/`，新功能先检查是否已有可复用的

## 踩过的坑
- [具体问题]：[为什么会踩、怎么避免]
```

这个模板大约 20 行。随着项目演进，踩了新坑就往"踩过的坑"里加，但总量控制在 40 行以内。

## 当前判断的最短证据链

这个判断由三个独立来源交叉支撑：

1. **"为什么会改不动"**：Towards Data Science 的"黑箱问题"分析指出——AI 生成的代码倾向于把不相关功能塞进单个文件（如一个 600 行的页面混合渲染、支付、校验、API），几周后回来修改时"唯一理解这些代码关系的是当时生成它的上下文窗口"。这解释了为什么三个月后维护成本急剧上升。

2. **"不约束会怎样"**：Dragos Nedelcu 写了 15 万行 AI 代码后发现——AI 不用已有库而自己重写功能、代码充斥无用文件、组件完全没有复用、60% 需要重构，最终执行 `git reset` 从头来过。这是不施加结构约束的极端后果。

3. **"约束了会怎样"**：HN 上 newspaper1（30 年开发经验）和 abustamam 的成功实践——前者在生成前写详细文档作规格、小步推进；后者为非技术团队成员配备了架构规范和自定义 linter 作为护栏。两者都通过"生成前约束"而非"事后逐行审查"取得了好结果。

- 来源层级：社区一线经验（多个独立来源交叉验证）
- 仍未闭合的关键缺口：缺少量化数据——生成时约束到底能把"三个月墙"推迟多久，目前只有定性证据

## 成立前提
- 项目性质是个人工具/自用 demo，不涉及外部用户数据
- 开发者（你）能理解功能设计和实现逻辑，但不深入底层代码
- 使用的 AI 工具（Claude Code 等）支持 rules/约束文件

## 路径分流

### 三条路径重新定义（从细到粗）

| 路径 | 人类做什么 | 人类不做什么 | 与相邻路径的分界线 |
|------|-----------|-------------|-------------------|
| **A. 实现逻辑层** | 问 AI "你大致怎么实现的"，审实现思路，确认关键逻辑 | 不逐行读代码，不审语法/风格 | 与 B 的区别：A 会追问"为什么这样实现而不那样"，B 不问 |
| **B. 架构块层** | 只看"有哪几个模块"，确认结构合理 | 不问具体实现方式 | 与 C 的区别：B 会看模块划分，C 完全不看中间过程 |
| **C. 意图-验收层** | 只给一句话需求，最后验收结果能不能用 | 不看任何中间过程 | 最粗粒度，"能跑就行" |

### 按场景分流

| 场景 | 推荐路径 | 理由 |
|------|---------|------|
| 一次性脚本、数据处理、不再改的工具 | **C**（纯 vibe） | 不需要维护，坏了重新生成比修更快 |
| 会持续使用但改动少的个人工具 | **B**（架构块层） | 确认模块边界清晰即可，偶尔改动时能定位到正确模块 |
| 会持续迭代、功能逐步增加的个人项目 | **A**（实现逻辑层） | 需要理解实现思路，否则到第 4-5 轮迭代时地基会塌 |
| 涉及 API 密钥、登录、外部服务调用 | **A + 关键代码审查** | 即使是个人工具，密钥泄露的后果也不可逆（实例：AWS 密钥泄露→半小时被盗用发 8 万封邮件） |

### 暂缓 / 放弃
- 暂缓：不需要对所有个人项目统一一个审查标准，按场景分流更实际
- 放弃：逐行代码审查——对个人工具场景成本远大于收益

## 当前证据可支持到的动作上限
路径分流 + 给出具体的生成时约束清单。证据不足以量化"约束到底能省多少维护成本"，但方向一致性很强（多个独立来源交叉验证）。

## 现在最值得做的下一步

### 1. 给你现在用的 AI 工具加生成前约束
在 `CLAUDE.md` 或 `.cursor/rules/` 中写入结构规则（参见上文"生成前约束具体是什么"一节的四类规则）。从最影响可维护性的两条开始：文件/模块边界 + 复用规则。

### 2. 对持续迭代的项目，每次改动前先 commit
实践者最推荐的轻量安全网。不需要写测试，但需要能回滚。

### 3. 维持路径 A 作为默认，但对一次性任务主动放手到 C
你当前的做法（问 AI 总结逻辑）已经是路径 A，不需要改。但对一次性脚本/数据处理可以更大胆地放手。

## 暂不动作
- 不需要系统化地让 AI 写测试——对个人工具场景，日常使用本身就是最好的测试
- 不需要引入 pre-commit hooks 或 CI——对个人工具过重
- 不需要担心安全漏洞统计——那些数据针对的是无工程纪律的 vibe coding 平台用户

## 观察信号
- 如果某个个人工具用了三个月后改动变困难→检查是否缺少生成时的结构约束
- 如果发现 AI 总结的逻辑和实际行为不一致→说明路径 A 的验证方式需要补强
- 如果开始做有外部用户的产品→重新评估，路径和风险矩阵都要上调

## 推翻条件
- 如果有证据表明"生成时约束"对维护性没有实质帮助→当前判断的核心支柱倒塌
- 如果你的实践中路径 A 反复出现被 AI 遮掩的关键问题→需要上移到更细审查

## 仍未解决的问题
- AI 对自己代码的逻辑总结的遗漏率到底多高？（缺少量化研究）
- Motivation 应该细化到什么颗粒度才够用？（已作为独立 research idea 记录）
